# 两任务改单与共享库存竞争的 HTTP 验收

基线为 PR #61 `5471a8d`。全部使用合成 seed、真实 loopback Uvicorn HTTP 和返回 HTML。
这是两个客户端请求的模拟竞争，不证明多人认证、权限隔离或生产并发能力。

## 实际运行的场景

| 场景 | 执行与结果 |
| --- | --- |
| 两任务改单 | SO-1001 的任务 A 获得批准后，新建独立任务 B；A 被较新意图取代，旧提交返回409，无订单或库存效果。B 重新规划、批准并提交成功，A 再次提交仍被拒绝 |
| 先后争用库存 | B-BLUE-L 库存30、原预占10、可用20；SO-1001 和 SO-1002 各规划新增15并批准。一个提交后预占25、可用5，另一旧提交返回 STALE_DEPENDENCY，未超卖 |
| 重新规划 | 落后订单仍申请15时得到422 / SHORTAGE，提示缺口10，业务不生效；按当前余量改为5、重新规划并批准后提交成功，最终预占30、可用0 |
| 同时提交 | 两个独立 HTTP 客户端同时提交上述两个批准，一个成功、一个409；失败方重新规划5后成功，最终仍预占30、可用0 |
| 重放 | 已成功的原键回放返回原 operation，数据库 dump 不变；过时批准不能变成第二次业务 |

审批前没有业务写入；失败没有额外预占。结果仍明确为 partial / global_completeness=not_assessed。
实际 typed `/plans` 请求明确给出 SKU、数量和当前版本，未使用模型推断这些修改。

## 发现并修复的 P2

基线的提交检查没有放过超卖，但库存变化后，页面已显示 STALE 并禁用批准，
批准 API 仍可能返回成功：既可返回尚未到期的旧批准，也可在失败提交撤销批准后生成新批准。
这个新批准的提交仍会因库存版本变化失败，用户得到“批准成功”却不能继续。

现在 `approve_plan` 在现有 BEGIN IMMEDIATE 内、返回旧批准或写新批准前，
检查本计划绑定的库存版本；缺失或改变时返回409 / STALE_DEPENDENCY，
提示核对可用库存、重新规划并批准新计划。拒绝不新增或改写批准，不更新计划绑定的库存版本，
不能通过重新批准把旧计划自动升级为最新库存计划。原提交版本检查继续保留。

过时或被替代的任务页新增下一步：核对当前订单、库存和最近任务；
若其他任务已完成目标，不重复执行；确需继续时基于最新数据重新规划、重新批准。
页面不自动重放、不生成新提交标识、不替用户批准。

这次修复只涉及已复现的库存批准不一致与过时页面说明。
没有改变库存分配规则、批准有效期、意图接管、核验范围或业务提交协议，也没有新增迁移。

## 回归与边界

`tests/test_competing_order_journeys.py` 使用真实 HTTP 验证旧有效批准和失败后批准两条路径，
拒绝批准时整个数据库不变；并验证同订单较新意图、同时提交、缺货拒绝、重新规划、预占合计和原键重放。
新测试也检查页面下一步以及有限核验不被表述为全库通过。

仅验证合成固定规则、同机 SQLite 和 HTTP/HTML；未验收真实浏览器交互、自由语言、真实 ERP 或模型。
身份仍为本机演示身份，父链与完整共享依赖证明仍未实现。本轮未合并、部署或重试 PR 正文操作。
