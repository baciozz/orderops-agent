# 自动核验中的执行证据拦截

基线为 PR #61 `d3856c9`。本片围绕实际业务复现推进：调度、批准、业务事务提交后，
在首次回读前删除当前 MTO 行及订单全部关联。旧现存事实检查返回空问题并清 pending；
现在同一核验尝试还要比较该 operation 的保留执行证据，发现行及关联缺失后保留 pending。

## 可以作出的结论

现存事实检查和单次操作的执行字段审计都在同一读事务内运行。发布时仍在固定物理连接上检查
SQLite data_version；若期间有提交，进入 BEGIN IMMEDIATE 后完整重跑两种检查。
所有结果（包括差异、证据不足）都在写事务内验证 token、未过期租约与结果新鲜度，序列化后再验租约。
旧成功不能覆盖新接管者的失败，任何写结果异常都不清 pending。

Operation 新增可空 `verification_observation`，与业务 `result_json` 分离。协议为
`execution_guard_v1`，记录观察时间、现存事实检查结果、完整限定字段报告及以下状态：

| 状态 | 含义与调度 |
| --- | --- |
| partial | 现存事实检查未发现矛盾，本次提交保留的行、关联、预占流水一致；结束此次回读及其重试 |
| findings | 至少一项可观察事实存在矛盾；保留 pending，按原预算重试/转人工 |
| inconclusive | 保留证据缺失、损坏、不支持或超出限额；保留 pending，不把缺失当空集合通过 |

**所有状态的 `order_graph` 都是 inconclusive，`global_completeness` 都是 not_assessed，
`authorizes_business_action` 都是 false。** 没有新的可信根、父链或共享依赖证明。
`committed_verification_pending=false` 只表示已有回读检查完成，不能作为整单/全库可信或业务放行依据。
原现存事实检查失败仍可阻止结束回读，不能由限定字段一致覆盖它。

这是用户选择的部分核验语义接入，不是将单次执行增量升级为完整图。
若故障发生在第一次保留证据之前，新批准仍不能认证未知父图；报告可能只有字段 partial，整单始终不确定。
若最新操作不含旧取消锚点，它不能代替旧操作的历史审计。尚未实现跨代闭包与连续失效监控，不能声称
所有历史断链、所有已完成操作或整个数据库已自动得到覆盖。

## 用户流程与接口

真实任务 `/tasks/{id}/view` 的 `result.verification` 现在返回 pending、partial 或 unassessed；
本实现不再生成笼统的 passed。新增 `verification_details` 携带上述记录。已有客户端必须接受新增字段
和状态；不能将“非 pending”解析为整单通过。数据库旧记录没有观察时，即使旧 pending=false，也显示 unassessed。
读取页面/API 不补记录、不重新核验。模板显示字段差异、未覆盖对象及时间，并声明观察不持续保证当前状态。
页面的限时更新提示也比较观察时间和状态，仍不自动批准、提交或重载。

业务提交成功仍为 SUCCEEDED，核验异常不诱发重提；业务审批规则没有因 partial 放宽。
同键重放保留原 operation。自动调度只重试 pending，不扫描全部已完成操作。
`verify-operation` 对已完成操作也会获取独占租约并重新读取；旧记录缺证据时转入不确定/人工状态，
不会直接返回旧成功。已有 pending 且未转人工、或已有有效租约时仍拒绝抢占。
该命令可写核验元数据，不修复任何业务事实。退出 0 仅表示限定检查完成，绝不是整单通过。
实际 MTO 恢复测试还确认：另行批准的新修订可恢复当前需求并得到自己的 partial，
但不会修复旧修订已经丢失的行；旧操作的历史差异继续保留 pending/findings，不能被新业务掩盖。

## HTTP 写入失败与恢复

父线程在真实 HTTP 验收中发现：证据 INSERT 失败虽然回滚正确，但未处理异常被 Uvicorn 输出，包含 SQL 参数。
现在保留证据的 SQLAlchemy 写入异常转换为 `503 / COMMIT_STORAGE_FAILED`，静态消息说明回滚及原键重试。
错误离开业务事务，回滚完成后才由 API 返回结构化响应；不消耗批准，也不留下 operation、业务修订或 outbox。
SQLite engine 设置 hide_parameters，默认异常表示不打印绑定参数。

HTTP 中间件对其范围内未处理异常返回静态 `500 / INTERNAL_ERROR`，不将原异常继续交给 Uvicorn 日志。
通用 500 不声称回滚（异常可能发生在提交之后），也不声明可以盲目重试；应保留原标识核对状态。
结构化事件的正常请求/计划/批准关联 ID 仍按原日志协议保留；修复针对原始异常、SQL 与业务载荷泄露，
不是清除所有可追踪标识，也不是对任意第三方 logger 或响应开始后的流式异常作全面保证。

`tests/test_http_storage_failure.py` 启动真实 loopback Uvicorn 子进程，通过 HTTP 完成调度和批准，
使用合成 SQLite trigger 使证据写入失败；验证结构化响应、完整数据库 dump 不变和日志没有 SQL/载荷，
删除故障后原幂等键成功且重复请求无新增。未使用浏览器、外部网络模型或真实数据。

## 迁移与回退

新增迁移 `execution_verification_guard`，接在 `execution_evidence_binding` 后。
只新增可空 JSON 列，不回填、不改旧 pending/批准/回执。旧观察始终保留原含义，读取不会认证历史。
已有证据、绑定或观察记录时，降级第一步就拒绝删除并保留 schema 版本；空库可往返。
单迁移 DDL 前、DDL 后及版本标记故障已验证回滚/重启，不能据此声称整条迁移链原子回退。

切换前必须停写并关闭全部旧 API、worker、watchdog、CLI、脚本及 SQLite 连接，保留一致备份后显式迁移。
此保护只约束当前应用路径；旧 writer/直接 SQL 可忽略新列，外键关闭也不形成隔离。
回退使用理解新证据/观察的兼容版本；不能通过丢弃观察把 partial 或 unknown 还原成旧 passed。
本轮没有部署切换，也没有完成认证授权或独立 writer 身份隔离验收。

## 已执行验证与剩余边界

业务测试覆盖变更/新建、提交后全断链、原件恢复、幂等重放、重启后的人工核验、旧证据缺失、
新批准无法认证未知父图、旧成功与新失败交错、相关事实并发改变、结果写入异常及迁移中断。
既有取消、部分尾单、共享库存、租约、回退和恢复套件继续作为门禁。
人工浏览器与自由语言能力未验证；离线 fixture 通过率不能替代它们。

下一步仍需真实批准父链/取消锚点、权威共享成员闭包与各写入路径的一致协议；当前 partial 不是这些能力的替代。
