# 清单协议的共通安全门槛与验收

基线：PR #61 `8fa671e873a1254c59df383ab7d98e28b973fba8`，2026-11-06。
补充 [清单设计](LINK_MANIFEST_DESIGN.md)。本次只有设计与合成测试；没有批准 v2、生产清单、
业务门禁、schema 迁移或旧数据接纳实现。用户已选择明确范围的部分核验，后续契约与实验见
[范围核验协议](SCOPED_VERIFICATION_DESIGN.md)；该选择没有豁免以下共通门槛。
**当前“行和全部关联同时消失”盲区没有关闭**。

## 核验结论与业务提交阻断是两件事

现有 `committed_verification_pending` 表示已经提交的业务尚待核验，不是全局业务互斥锁。
合成实验让核验连续失败，两次业务提交仍依次产生修订 2、3；两个操作均保持 pending。
不能把“严格全库核验”悄悄解释成“任何未知旧订单都禁止所有业务写入”。

| 判断 | 共通要求 | 产品选择及实施边界 |
|---|---|---|
| 核验结论 | 不完整、损坏、未知协议/来源不能报通过；报告保留范围、未覆盖依赖、root/协议版本及时间快照 | 已选择明确部分结论；不得把部分通过复用为全库通过，未知依赖仍使相关命题无法通过 |
| 新业务提交 | 对本次实际写入依赖的订单、父清单、批准、根、归属及共享事实，同一写事务内校验；依赖不能证明则不能把本次写入当作已获有效授权 | 未知的其他订单是否阻断该提交、旧协议能否继续人工处理，以及来源接纳资格；本轮不新增这些规则 |
| 已提交操作重放 | 保持原 operation/幂等键和提交事实；证据缺失不能导致重新执行业务或伪造清单 | API 如何显示“已提交、核验未完成”；不能用普通“未提交”错误诱发换键重提 |
| 核验后事实变化 | 原成功只适用于当时范围/根状态；新损坏须可发现，不能用旧成功放行 | 持续监测与结果失效调度；现有 pending=false 并不意味着持续核验 |

核验完成与允许业务动作应为两个显式状态，不从一个布尔值推导另一个。
未来拒绝新业务时要求业务修订、关联、库存流水、批准消费和业务 outbox 零新增；
明确的批准撤销/失败审计可按现有规则单独记录，不能误报为业务提交。

## G1：可信父链需要来源授权及事务内重验

当前 header 的 digest 正确，只证明内容匹配摘要。所有父摘要重算一致，也不能证明历史节点
由合法批准产生。每个保留节点或正式可信检查点至少需要：

- 精确订单、修订、父节点 ID/digest/格式；修订递增、父归属一致、无环、无未说明断层。
- 保存的规范批准载荷、Plan/Approval 哈希与消费状态、对应 operation/request/receipt/audit
  身份，及回执承诺的清单摘要。不能只有可变计划 JSON 或一个“已验证”标志。
- 完整根引用集合：当前节点、父链、取消/历史锚点使用的 root ID、generation、digest、
  来源类别、状态、单调递增 trust epoch。新批准绑定这个依赖闭包。
- 原批准证明或根不可验证就报告 unknown。外部可信备份/接纳依据是另一个明确过程；
  不从剩余记录生成可信度，不声称数据库内哈希可以抵抗全库一致重写。

计划阶段读取仅用于提案。提交 `BEGIN IMMEDIATE` 后重新读当前指针、所需授权/父链/根状态/
锚点/归属及实际业务依赖，再比对新版批准；核验成功缓存不能替代。依赖变化即使没有改变
订单修订号，也使旧批准失效。根撤销后再接纳，即使 digest 恢复原值，递增 trust epoch
也应使旧批准失效，避免“撤销—恢复”绕过批准绑定。

在写锁内完成验证和写入，排除检查与业务写入之间的其他 writer。释放锁后事实仍可能变化，
所以提交后检查继续使用现有固定连接、data_version 重查、租约/所有权和写结果事务围栏。
旧 WAL 快照不能证明发布结果时仍有效。超深链、超限、未知版本均为未完成验证，
不能截断祖先后返回通过。

## G2：取消锚点和多代根不能被最新根覆盖

取消锚点绑定 typed doc ID、订单、真实存在的取消修订、取消 operation、源清单及其批准/
回执、DocRevision 内容、原 root ID/generation。源节点必须属于该订单的授权祖先，
不能用另一订单同号修订、未来修订、同数量单据或当前 CANCELLED 标签替代。

后代完整图继承取消锚点。零数量、后续 STOCK 修改、切换新根都不能自动删除它，也不为了
核验而伪造指向新修订的取消关联。部分尾单与已执行部分保留各自明确身份。
新根 g2 不自动证明 g1：只要当前图/锚点/必要历史引用 g1，就必须同时验证 g1。
旧根丢失、撤销、ID 复用或证据损坏，不能被可读的 g2 header 掩盖。

根引入、接纳、撤销、替代及 checkpoint 应形成有身份、原因、范围、时间和批准的不可变事件；
generation 和 trust epoch 不复用、不回退。根替代明确携带所有历史依赖及取消锚点，
不是把旧图复制到新根后就自动可信。分叉、同代多头、跨订单争用根应停止验证。
删除旧根/历史的条件必须由正式保留与 checkpoint 协议证明；没有协议时保留依赖，不能借
存储清理或“最新版本”规则跳过。恢复原件与重新接纳应区分，后者不能伪装成原批准。

## G3：跨订单归属冲突不能被核验范围过滤掉

现有 DownstreamLink 唯一约束是 doc_type/doc_id/link_seq；实验确认它允许同一生产单以
不同序号关联两个订单。这证明 schema 的能力，**不等于声称所有当前热核验都会漏报冲突**。
未来限定范围检查也不能只读目标订单后宣称归属唯一。

若采用一单据归属一订单的协议，建议有独立 typed document claim，唯一键
`(doc_type, doc_id)`，绑定归属证据、订单、来源根/generation 和生命周期；结合全局事实关联
索引检查重复、额外和冲突。约束是互斥手段，不是归属证据本身。不能用 `INSERT OR REPLACE`
或无条件 upsert 把已有 owner 覆盖成新 owner。

同一业务事务取得 claim 并写完整清单/效果：两订单竞争同一新 ID 时一方成功，另一方业务、
批准消费、库存及 outbox 回滚。取消保留归属/tombstone，不能自动让出 ID。MO 与 PO 的同
字符串 ID 是不同 typed identity；SKU、数量、父 MO 不是所有权键。
缺少 claim 不证明单据未被管理：旧库、遗失证据、未登记历史均须 unknown；新建单据还需
批准中的“该 ID 不存在”依赖与当前事实重验。

若产品允许共享生产单、合法转移或重新激活，需要显式分配/转移协议及双方来源证明。
本轮不选择这种语义，不自动迁移或纠正冲突；无明确证据不能擅自选定一个订单。
即使报告范围限定为 A，也检查其单据是否被范围外 B 声明或关联；共享库存等依赖同理。
范围闭包不能证明完整时，结论为未完成验证。

## G4：隔离所有旧 writer 和关闭外键的连接

writer 不只有 `commit_plan`。上线清册应逐项提供实际进程/版本/连接证据：

| 路径 | 必须覆盖的写入 |
|---|---|
| API/kernel、表格/输入、计划与批准 | 提交、订单意图、来源/批准依赖、重复请求 |
| verification 自动/手工重试与初始回读 | pending/manual、结果、重试预算、租约、核验成功发布 |
| worker、sync_dispatch、watchdog、recovery | 任务接管、重放、确认和恢复分支 |
| inbox/outbox/dispatch | 消息、任务、交付；旧恢复路径不得触发旧提交 |
| receipt/cut、seed、导入、运维 CLI、迁移/恢复脚本 | 库存/生产事实、关联、快照、schema、数据库替换 |
| 直接 SQLite、连接池、外部进程和旧安装包 | 未经过启动检查的写入、关闭外键的连接、已打开的文件描述符 |

只升级 `schema_ready` 或增加 SalesOrder 指针外键不足。真实 kernel 实验显示：已存在的
旧 verifier 在未来 schema 标记下仍能清除 pending；它不更新 SalesOrder，订单复合外键
不能阻止这种发布。

SQLite foreign_keys 是连接设置。另一个 OFF 连接可以写入缺失 header 的指针，之后 ON
连接仍读到坏数据；开启外键不修复历史损坏。唯一约束不受该开关影响，但可写连接仍可改
owner、删表或改变规则。实验的 epoch trigger 能拦截遗漏新字段的旧 SQL，却挡不住复制
公开 epoch 的直接连接：epoch 是新鲜度标记，不是身份凭证。

正式切换的共通要求：

1. 停止接入和全部旧 writer，等待/中断在途事务，清空任务执行/回调，关闭连接池，并验证
   旧进程无法恢复写入。单纯改文件权限不会可靠撤销已打开的文件描述符。
2. 对数据库及 WAL/SHM/目录建立写权限边界，仅受控新 writer 可写；需要时使用独立身份的
   单一数据库写入服务。不能让旧 CLI 与新服务共享无限制文件写权限后仅靠自报版本。
3. 新建及复用连接在写事务前检查 schema/protocol/writer epoch、外键状态及连接配置。
   约束/触发器是额外防误用层，须覆盖 Operation 结果发布等写表，不能只保护订单修订。
4. 显式迁移前后进行一致备份、foreign_key_check、来源/所有权检查及 writer 清册验证。
   迁移、恢复、升级中断与降级另行验收；无 writer 隔离证明就不能启用新核验。

本轮仅在临时数据库改变 PRAGMA/触发器，未修改真实运行权限或实施进程切换。
SQLite 内的一张 epoch 表无法对拥有同一数据库文件写权限的任意进程建立身份边界。

## 验收矩阵：实验不等于生产验收

运行 `python -m pytest -q tests/test_manifest_common_gates.py tests/test_link_manifest_design.py`。
`tests/manifest_lineage_model.py` 与业务模块无调用关系；根和逐节点批准摘要由合成 fixture
提供独立见证，不从剩余行推导可信，不实现真实 Plan/Approval/receipt 的验证链。
部分故障实验刻意授予畸形节点合成见证，以检验结构校验仍会拒绝；这不是生产接纳工作流。
模型只支持本实验的取消状态，不是通用图解析器或安全库。

| 门槛 | 合成实验/反例 | 生产验收标准（尚未完成） |
|---|---|---|
| G1 父链 | 父/祖父缺失损坏、外订单父、截断、环、深度超限 | 所有路由返回稳定未完成/拒绝原因，不截断成功 |
| G1 授权 | 缺逐节点见证、全链重哈希但无对应见证 | 每节点/检查点绑定实际已消费批准、回执和身份；原件缺失不重建可信 |
| G1 新鲜度 | 旧 WAL 快照、根撤销后恢复、父证明变化 | 提交事务读完整依赖闭包比对批准；业务零写入，旧批准失效 |
| G1 原子窗口 | 检查后竞争 writer 被锁阻止；提交后新损坏可发现 | 真实事务和 `_post_verify` 覆盖所有新依赖；过期租约/旧成功不能发布 |
| G2 取消 | 缺锚点、后代丢弃、未来修订、错 operation/祖先/归属/单据/根代 | 证据属于真实祖先；跨根继承，不伪造新关联 |
| G2 根 | g2 可读但 g1 缺失、撤销、身份复用 | 引用旧根仍有效；根事件单调有授权，checkpoint/保留独立验收 |
| G3 并发 | 两订单同时 claim 只有一个效果；FK OFF 不破坏唯一约束 | 批准消费、业务效果、全局 claim 同事务；冲突方完整回滚 |
| G3 生命周期 | 取消不释放；不同类型同字符串合法；owner 改写被发现 | 跨范围检查所有权；共享/转移有明确协议，不无条件覆盖 owner |
| G4 旧 verifier | 未来 schema 标记仍挡不住旧 `_post_verify` | 初始、重试、手工核验、在途结果分别验证切换隔离 |
| G4 连接权限 | FK OFF 绕过外键；公开 epoch 可仿冒 | 实际身份和已打开连接隔离；迁移中断/回退、所有 writer 清册验收 |
| 语义分离 | 两个 pending 操作仍提交两个修订 | 核验范围与业务阻断分别明确，不把部分核验选择解释成新增全局阻断 |

实验仅证明列明机制和反例；不证明真实 v2 批准绑定、全写入路径隔离、自动来源接纳、
迁移/回滚或自动核验已可上线。此前单事务回执、幂等与恢复实验继续保留。
本轮无 schema 或生产行为变更；回退仅移除文档和测试，不需要数据库回滚。
