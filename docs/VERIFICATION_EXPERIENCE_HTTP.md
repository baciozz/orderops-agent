# 核验范围与下一步的 HTTP 体验验收

本轮先以真实本地 Uvicorn 和合成数据执行订单变更，固定基线为 `302b122d7ea05e3eb50094f5041c21b34d781d6d`，没有通过浏览器或真实模型验收。

## 实际复现

1. 新任务完成黑 M 未发 40 件改白 M，批准后提交成功。API 返回 `partial`，并明确 `global_completeness=not_assessed`。页面虽已有整单不确定声明，具体字段却直接显示 `revision_lines / consistent` 等内部名称；八项未覆盖对象的原因也只有英文码，且结果区没有下一步。
2. 使用归档的真实旧版 main `f5e8ecdca79d93e737d8151dc72239668a49c5a4` 创建并提交另一条任务。当时 API 为 `passed`；停止旧程序后，用当前 `init-db` 迁移同一数据库。所有旧表原有列值保持不变，新 API 正确显示 `unassessed`、无范围记录。页面结果区只剩“旧核验记录；来源及覆盖范围未评估”，没有范围解释或处理指引。
3. 对迁移后的旧提交实际运行 `verify-operation`。因旧版没有保留执行证据，退出码为 1，API 为 `pending`、需人工处理，观察为 `inconclusive`；业务记录不变。页面仅显示内部原因码 `EXECUTION_EVIDENCE_NOT_RETAINED`，不足以说明为何仍无法确认。

这些是可复现的展示缺口。本轮只改模板，不改变审批、提交、核验判定、API、证据或历史业务记录。

## 页面调整

- 有提交回执时，统一说明“已提交不等于整单核验通过”，提醒不要重复提交，也不表示整单/全库通过或获得新的业务权限。
- 将本次修订行、提交关联、预占/释放流水的字段与状态说明为中文，显示证据项数和本次读回项数。未覆盖对象仍逐项保留真实 ID，并解释父版本来源、单据历史、共享库存范围等未证明原因；内部码保留在 HTML 数据属性中供 API 对照。
- 没有范围记录、没有字段对照或没有对象清单时，明确“无法确认”“不能理解为全部覆盖”，不把空列表当作全部通过。
- 用已有当前订单、任务审计摘要入口支持核对。审计不含原件，也不是完整来源证明。来源不明需维护人员依据可信原件、审批与执行记录人工核对；不提供自动补证、自动标全过或重新执行业务的入口。
- 保留核验观察时间和待处理进度；没有持续监控保证。未识别原因仅提示维护人员核对，不推断为一致。

## 复测证据

真实 HTTP 重新执行新任务，以及真实旧版创建 → 停服 → 迁移 → 查看 → 只读复核的完整链路。新任务的 API 仍为 `partial`，父链与共享依赖仍不确定；旧任务仍先 `unassessed`，复核后证据不足并转人工。页面覆盖对象、原因、字段状态及项数与 API 对应，链接实际返回 200；读取页面和 API 不写数据库。原提交键重放仍只返回原 operation，没有新增订单、库存变更或来源认证。

`tests/test_verification_guidance_http.py` 用真实 HTTP 回归新任务、字段/对象与 API 对照、可用链接和只读性；既有 legacy 形状回归增加旧记录及证据不足页面断言。真实旧程序迁移实验独立执行，旧业务数据没有为构造结果而清空或重写。

这不是普通用户访谈、真实浏览器交互、自由语言理解、ERP 或生产就绪证明。整单来源证明仍是明确未覆盖的产品边界。
