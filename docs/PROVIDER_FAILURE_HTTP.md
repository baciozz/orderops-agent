# 本机模拟提供方：失败提示与安全重试验收

复现基线为 PR #61 `276953b9a83e038823bb18670c0e5a1230c0697c`。使用合成 seed、本机 HTTP 模拟提供方和真实 Uvicorn HTTP/HTML，没有连接外部模型或 ERP，也没有操作浏览器。

配置的 `LIVE` 是应用的运行路径标签；模拟服务只返回预设 JSON，不是语言模型，下面结果不构成真实模型或自由语言验收。模型用量表记录的是模拟请求的本地账本，没有真实费用。

## 实际运行

对同步 `POST /dispatch` 和持久 `POST /inputs` 两条路径各运行四种故障，共8条旅程：

| 本机提供方行为 | 任务实际结果 | 恢复前提供方请求数（每条旅程） |
| --- | --- | --- |
| 延迟1.3秒，应用读取超时为1秒 | FAILED / MODEL_TIMEOUT | 1 |
| HTTP 200、有用量字段，但消息内容不是有效 JSON | FAILED / SCHEMA_INVALID | 3，沿用现有格式检查次数 |
| HTTP 503，错误消息含合成私有标记 | FAILED / MODEL_UPSTREAM | 1 |
| 接受请求后断开连接，不返回 HTTP 响应 | FAILED / MODEL_TRANSPORT | 1 |

持久任务由独立本机进程调用现有后端 `run_once`，明确使用该模拟提供方配置。公开 CLI 与网页演示 worker 保持 FIXTURE-only；本次没有增加 LIVE worker 产品入口，也没有证明用户能够仅靠现有网页完成 LIVE 全流程。

每条旅程实际检查：

1. API 状态为 FAILED，没有计划、批准或 operation；页面的批准、提交按钮禁用。订单修订、行、库存、预占、生产采购事实及业务流水不变。输入和失败轨迹、用量等工作流记录会保存，已选择订单的意图版本会推进；这不是“数据库完全没有变化”。
2. 本次调用的用量记录全部结算。超时/连接中断按授权上限保守记账；格式错误保留提供方报告的合成用量；503无用量时仍占调用次数。这不表示已验证真实提供方账单。
3. 恢复模拟提供方后，使用原输入键仍得到原失败任务，整个数据库不变，也不新增提供方请求。FAILED 是终态，不原地重置尝试预算或自动重新执行。
4. 人工确认继续后，以新输入键创建新任务。计划进入待批准状态；批准本身不改业务。另行提交成功，最终每库只有一个 operation、一个批准；原提交键重放不新增记录。结果仍为 partial / global_completeness=not_assessed。
5. 页面及应用日志不包含模拟提供方的私有错误正文；没有通过显示 `result_ref` 来解释异常。

## 实际复现并修复的 P2

上述8条链路在基线都能安全失败并以新任务恢复，但页面统一显示“暂无法提供此失败的安全说明”，不显示已知错误类别，也没有解释原键不会重试、可能已有用量，以及如何回到原 LIVE 接入。用户无法从页面区分等待提供方恢复与反复重放旧请求。

本轮只补充这四类已复现失败的静态原因和下一步：先核对服务恢复、当前订单/库存及最近任务，再明确创建新任务，重新核对计划、人工批准和提交；说明演示入口及 worker 不能恢复 LIVE 任务。已有执行记录时仍先要求核对，不引导直接重建。未识别错误继续显示保守的维护人员指引，不回显上游正文或任意异常。

不改变提供方调用、格式重试次数、终态、用量结算、幂等、审批/提交、核验规则或数据结构；没有新增迁移。

## 可重复执行及边界

开发环境运行：

```sh
python -m pytest -q tests/test_provider_failure_journeys.py
```

测试启动两个本机 HTTP 服务，独立数据库、明确配置和预设响应；无需真实凭据。基线在全部业务恢复断言通过后，8条均因缺少页面原因而失败；修复后8条通过。每条测试保留 `failure.html`、`journey.json` 和 `uvicorn.log`，用 `--basetemp` 可指定独立证据目录。

未验证真实浏览器点击/JavaScript、真实 DNS/TLS/代理、真实提供方认证/429/账单、模型自由语言、长文件、生产并发或 ERP。未知父图和共享依赖仍未证明；这次没有关闭认证授权或生产部署缺口。完整门禁及精确提交以本轮交付记录为准。

另见[取消、迟到响应及提交竞争验收](CANCEL_JOURNEYS_HTTP.md)，涵盖处理中的取消及重启/重放；仍使用本机模拟提供方。
