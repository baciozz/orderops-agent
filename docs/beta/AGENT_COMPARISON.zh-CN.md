# 单Agent与双Agent：最小只读比较

用户于2026-11-09追加耗时、正确率、费用与失败比较；未预设哪种方案胜出。**评测专用适配层已实现并在MockTransport实测，尚无真实双Agent数据，产品运行架构不变。** 不得在简历写“多Agent更快/更准/节省X%”。

产品新清单入口是一次模型提案加确定性规则与人工确认。旧调度也是parser一次模型，inventory-check/doc-check为`uses_model=False`并顺序执行；FIXTURE trace的0ms/0tokens不是性能证据。不能将函数数目当模型Agent数，或把输入/权限不同的两个入口直接比较。

## 必需简单基线与可选双Agent试验

原方案简单基线仍是`benchmarks/review_baseline.py`：同一次提取的原始提案与规则后结果配对保存，复用一份成本；已有9项Mock/故障回归。它衡量规则拦截和误澄清，不称单/多Agent提速。见[SINGLE_MODEL_BASELINE](SINGLE_MODEL_BASELINE.zh-CN.md)。

新增`benchmarks/compare_readers.py`只用于合成开发/验证样本，不连接产品路由、不写业务、不建立提供方或新账本、不读取参考、不加LLM裁判、不自动重试。协调者传入现有预算客户端、配置、会话和同一只读规则函数；没有可直接启用LIVE的CLI。

| arm | 调用 | 输入与合并 |
| --- | --- | --- |
| single | 1 | 产品冻结的提取提示、用户输入、快照与schema |
| double_same_prompt | 并行2 | 同提示独立复采样，作为分工消融 |
| double_roles | 并行2 | 相同用户输入/schema；通用提取A/独立复核B角色后缀，双方看不到对方答案 |

双调用全部结束并保留失败；业务意图及规则状态/行都一致才形成候选，分歧或任一失败交人工，不挑胜者、不取动作交集。两个澄清候选的追问合并后再核对，语义是否完整由真人另评。两者一致仍可能共同出错，规则阻断仍阻断；每份原始提案与合并结果都要评分。所有结果需要人工确认，适配层没有业务执行权。

只接受冻结产品提示/schema和合成快照；输入字段限应用公开字段，不允许`expected`等元数据。人工转录另设辅助组。角色后缀仍受相同提示长度限制。工具不能识别客户文字里伪装的答案，协调者仍须验证输入来源。

from benchmarks.compare_readers import run_arm, schedule

# 推理前固定、保存并散列；索引不是模型输入。

record = run_arm(

    settings=frozen_settings, sessions=existing_shared_round_sessions,

这是已配置协调实例的接口示意，当前没有真实调用。两个client必须使用**同轮账本**及相同模型/参数/输出上限；工具不认证real/mock声明，也不保证调用方传来的client属于同配置。模型、账本ID、传输次数须协调者核对。

## 公平执行与预算

先固定10个开发+10个验证样本，各重复3次、各arm都跑：single60次，双同提示120次，双角色120次，共300次。`schedule`以固定种子洗牌样本、轮换arm顺序；不看结果挑案例。20例是小规模开发实验，不是正式保留准确率；不拿两条已调优例子代替。

同模型、原件、OCR/映射、工具权限、推理/输出上限、环境与账本；同一时间只跑一个arm，双组内2并发是实验因素。所有超时、拒绝、无JSON、分歧和误澄清入分母。A/B、合并、规则后结果分别保留，不只评分一致样本；来源/澄清按[评分候选](EVALUATION_PROTOCOL.zh-CN.md)真人复核，AI自评不能变真值。

沿用既有保守单次≤$0.004估算，300次上界约$1.20，**不是实测费用**。从原可选开发/验证额度调配，优先正式功能/风险/稳定性和最终演示。配对基线复用一响应；正式方案若独立另跑必须实计，不能混用节省数。统一协调者先重算全轮剩余$5/1000调用槽，当前已报告42次/$0.009299；不足时暂缓可选对比，不另开账本。价格/型号调用前由统一任务核实，本实例不重复付费。

## 计时和已验证边界

记录保留原始响应、错误码、客户端尝试数、各调用时间、整体墙钟和账本条目。`wall_s`只含模型客户端加本地合并，**不是上传/OCR、浏览器、人工等待或导出的端到端耗时**；完整链路另用实际浏览器计时。不以残差冒充规则耗时。p50/p95在全部尝试上报告并另列成功子集；费用含失败预留，按故事及成功任务计算。HTTP请求数/缓存无法验证时保持null/unknown。

双Agent墙钟可能接近两调用最大值加合并，成本通常增加，质量、分歧率和总耗时未知，没有必然优势。`accuracy/advantage=null`直到有可信标签和真实数据；协调者还需补正式聚合、完整索引对账及浏览器耗时，工具不自动发发布结论。

8项实际离线测试覆盖三arm、同输入/schema、LiveLLMClient的MockTransport并行屏障、分歧、相关错误被规则阻断、同账本仅余1槽时一调用拒绝且不重试、标签字段拒绝及合并计时。实际注入150ms合并延迟复现旧计时遗漏（报告53ms/实际整体210ms），修复后报告183ms、整体197ms，包含该延迟；数值只说明计时范围修复，不是模型速度比较。只证明机制，产品没有变成多模型调度。可用表述为“实现只读双提取评测及同提示复采样消融，真实对比待完成”。
