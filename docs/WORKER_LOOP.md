# 操作者显式启动的有界 FIXTURE 循环

`worker-loop` 是离线合成数据演示的有界命令，不是常驻服务或生产就绪证明。
导入模块、启动 API 或 FastAPI lifespan 都不会启动它。不安装服务、不部署、不安排定时任务。
需要重复启动或长期托管时，由操作者另行负责；本次实现和验证没有运行实际常驻进程。

## 手工使用

先按 README 初始化合成演示库并载入 seed，然后由操作者另开终端运行：

```bash
python -m app.cli worker-loop --interval-seconds 5 --max-iterations 60
```

- 默认间隔 5 秒、最多 60 轮。间隔接受有限数值 0.1–3600 秒，轮数接受整数 1–10000。
  0、负数、NaN、Infinity、超界数值和非整数轮数均在打开数据库前拒绝，退出码 2。
- 每轮严格串行执行现有 watchdog 扫描、最多一个 `run_once` 任务和本地 outbox 投递。
  不新增领取、租约或 fencing 规则，不创建并行循环、线程池或子进程。
- 无论是否领到任务，每两个成功轮次之间都会等待完整间隔；最后一轮后不等待。
  因而间隔是“本轮结束到下一轮开始”的时间，不是固定启动频率，也不会为追赶积压连续空转。
- **只有轮数有上限，不保证墙钟总时长。** watchdog / outbox 沿用现有扫描范围，积压很大、
  单轮耗时长或数据库锁等待都会延长总耗时和停止延迟。60 轮不能解释为严格 5 分钟超时。
- 新命令总是复制传入的 Settings，并将副本的 `live_enabled` 设为 false 后传给扫描和任务执行。
  即使环境启用了 live，也不会创建 live 模型客户端，不修改全局设置；没有启用 live 的开关。
  FIXTURE 只保证模型执行离线，**不会鉴别数据库中是否含真实数据**，操作者必须指向合成库。
- 只推进已有任务规划、租约恢复、提交后的只读核验和本地 outbox 回执。不会自动批准计划、
  提交订单或修复业务数据。待批准任务仍停在 `AWAITING_APPROVAL`。
- 同样使用既有 CLI 的显式建表/迁移步骤。`worker-once` 的原调用参数、配置透传和单轮行为保持不变；
  两个 CLI 命令共用单轮函数。网页 worker 端点与 API 启动行为不变。

## 停止与错误

- Ctrl+C / SIGINT 或 SIGTERM 只设置停止请求，不向正在进行的事务抛异常。
  当前轮的扫描、任务执行和 outbox 完成后停止。CLI 信号处理器只修改无锁布尔标志，
  不调用 threading.Event.set 或获取线程锁；等待使用 monotonic 截止时间和最多 100ms 的 sleep 分片，
  空闲时停止检测延迟最多约 100ms，另受操作系统调度影响。
  停止后不再开始下一轮。重复信号也不会强行中断当前轮。
- 正常达到轮数上限或完成请求的停止，退出码均为 0，并输出完成轮数及
  `max_iterations` / `stop_requested`。此前信号处理器会恢复，数据库 engine 会释放。
- 现有组件已经处理的重试继续遵守其持久化计划：例如 outbox 失败退避、有限核验重试及耗尽后转人工。
  任务正常返回 `FAILED` 也不等同于循环崩溃，不会被循环无条件重试。
- 未处理的异常立即结束循环，退出码 1；不开始后续步骤或轮次，不吞掉错误无限重试。
  启动、迁移和清理异常也返回 1。输出只含固定提示和错误码，不打印异常原文或 traceback。
  本轮中已经提交的状态不会被伪装成回滚；操作者调查后可显式重启，沿用既有租约恢复与幂等机制。
- 强制杀进程、机器掉电、不可中断的阻塞及任意长事务不由优雅停止保证兜底。没有自动重启或外部告警。

## 可观测性

`oos.orchestration.worker_loop` 通过现有脱敏日志记录：

- `worker_loop.started`：FIXTURE、间隔、轮数上限。
- `worker_loop.cycle`：完成轮次、是否领取任务、恢复任务数、本地投递数。
- `worker_loop.wait`：轮间等待及 `task_claimed`。false 只表示没领取任务，不能据此认定没有核验等后台工作。
- `worker_loop.stopped`：完成轮数和停止原因。
- `worker_loop.failed`：未处理异常的固定错误码；CLI 边界另有 `worker_loop.cli_failed`。

沿用现有 INFO 事件级别；设置 WARNING 会隐藏这些事件，但 CLI 仍打印固定失败提示。
既有 watchdog / 核验 / outbox 事件提供逐项结果。不新增持久化指标，也不跨 CLI/API 汇总。

## 验证与边界

`tests/test_worker_loop.py` 使用注入的 clock、wait、stop 和临时 SQLite 合成数据验证轮数边界、
空闲等待、串行顺序、强制 FIXTURE、租约到期恢复、核验退避耗尽、outbox 到期投递和不重复业务提交。
信号处理器以合成调用及受控 signal.raise_signal 测试（包括持有 Event 锁时），启动/清理故障以注入测试，不运行后台常驻服务或真实模型。
`tests/test_cleanup_wiring.py` 继续覆盖 `worker-once` 旧参数和配置透传。

这不是托管调度器，不代表真实业务、生产负载、操作系统进程信号端到端验收或部署验收。
外部推送告警、长期调度和历史快照核验仍未实现。
