# 五分钟作品演示：有风险的服装改单（FIXTURE）

本脚本基于草稿 PR #61 的运行代码 `d6324e957be50ea18ce5248c55936b52eb722dfa`，尚未合入 main。先核对所用源码/安装包包含该版本。本轮已从全新 wheel 环境按 README 的隔离步骤完成真实 HTTP/HTML 验收；没有验证真实浏览器点选或录屏。

**这是五分钟讲解安排，不是安装耗时或浏览器操作速度承诺。** 请求提案由精确文本 fixture 提供，业务核对使用真实的确定性内核及合成 SQLite；不调用真实语言模型、ERP 或供应商。当前无认证授权，仅用于受控本机合成演示。

## 演示前准备（不计入五分钟）

按 [README](../README.md) 或[隔离安装指南第一节](NEW_USER_DEMO.zh-CN.md)装好候选版本和锁定依赖，设置 `PY` 为该安装环境 Python 的绝对路径。离线安装先准备匹配的 wheelhouse，使用指南中的 `--no-index` 方式。依赖安装不能算作现场演示的一部分。

以下与隔离指南使用相同的初始化和启动方式。新建目录，不删除原库，不在用过的库中重新 seed；`seed` 不会重置库存。只绑定 loopback，保持 LIVE 关闭。

```sh
DEMO="$(mktemp -d "${TMPDIR:-/tmp}/order-ops-demo.XXXXXX")"
mkdir "$DEMO/home" "$DEMO/tmp"
cd "$DEMO"
demo_python() {
  env -i PATH=/usr/bin:/bin HOME="$DEMO/home" TMPDIR="$DEMO/tmp" \
    OOS_DATABASE_URL="sqlite:///$DEMO/demo.db" OOS_LIVE_ENABLED=false \
    OOS_SOURCE_STORAGE_DIR="$DEMO/originals" \
    "$PY" -I -B "$@"
}
demo_python -m app.cli init-db
demo_python -m app.cli seed
demo_python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

每条命令必须成功。端口占用时确认原进程，不随意停止其他服务。该 DEMO 是可保留的独立演练目录；不要让系统临时目录清理承担备份责任，长期试用见[本地原件保存](LOCAL_SOURCE_STORAGE.md)。本场景只输入文本，不上传文件。

在允许使用浏览器的环境中，操作者可按下表预演；本轮只验证了对应 HTTP 请求和返回 HTML。现场点选前仍需自行预演，不能把本记录当作浏览器已验收。

## 五分钟主线

| 时间 | 操作与讲解重点 | 应看到的事实 |
|---|---|---|
| 0:00–0:40 | 打开 `/ui`，确认 FIXTURE；查看示例订单 `SO-1001`。说明客户要将 C 款黑色 L 全部改藏青。 | C 款 300 件，已裁 120，未裁 180。另有 A 款现货 100 件、已发 60，不属于本次修改。 |
| 0:40–1:20 | 进入“提交改单”，选择 `SO-1001`，把预填文字**完整替换**为下面的第一句；提交后触发 worker 一次。 | `NEEDS_CLARIFICATION`；提示已裁 120 件不能改色、未执行量只有 180；不可批准，尚无业务提交。 |
| 1:20–2:30 | 在**同一任务**回答下面的第二句，再触发 worker 一次。逐项核对旧新版与下游影响。 | `AWAITING_APPROVAL`；黑色保留 120、藏青新增 180，总量不变。已裁生产与已收货采购不改；未裁生产及未到料采购生成变更草稿。 |
| 2:30–3:15 | 明确点击“批准当前计划”，讲解批准与执行分开。 | 显示“已批准，可以提交生效”；订单业务版本与数量尚未生效，没有 operation。 |
| 3:15–4:20 | 单独点击“提交生效”一次，查看结果和当前订单。 | `SUCCEEDED`、订单 revision 2、一个 `operation_id`；核验为 `partial`，即限定字段一致，整单来源仍不确定。 |
| 4:20–5:00 | 展示已核对字段、未覆盖对象和下一步，下载变更清单；最后说明 fixture 与未验证能力。 | 本次修订行、提交关联及预占流水的限定对照；完整来源链和共享依赖仍未证明。不能把 partial 当整单/全库通过。 |

第一句，逐字输入（含空格，不加标点）：

```text
C 款黑色 L 全部改藏青
```

第二句，仅作为该待澄清任务的回答，不另建任务：

```text
只改未开裁
```

讲解可以这样收束：“客户确认只调整未执行部分后，内核重新核对计划，再由人批准并单独提交。这里展示的是合成业务的风险控制和可追溯结果；真实模型解析及 ERP 联调仍未验收。”

## 核对清单

| 对象 | 原状态 → 提交后的合成记录 |
|---|---|
| C 款订单行 | 黑 L 300 → 黑 L 120 + 藏青 L 180；A 款仍为 100。 |
| `MO-2001` / `PUR-3001` | 已裁 120 件、已收货黑面料 240 米：内容保持不变，只重新关联订单版本。 |
| `MO-2002` | 黑 L 180 件 → 藏青 L 180 件，已裁仍为 0，单据修订 2。 |
| `PUR-3002` | 黑面料 360 米 → 藏青面料 360 米，收货仍为 0，`PENDING_SUPPLIER`、单据修订 2。这只是沙箱变更，未实际向供应商下单或外发。 |
| 成品库存 | 全部余额、预占和原有 6 条库存流水不变；MTO 改色不产生现货预占。 |
| 提交与结果 | 一个 operation、一份执行证据、三行 CSV；核验仍是 partial，`global_completeness=not_assessed`。 |

批准前和批准后未提交时，订单业务修订、数量、生产采购及库存保持原样；输入、意图版本、任务与计划元数据会推进。成功后不要另建任务重复执行；HTTP 验收用原计划、批准和原幂等键重放，返回同一 operation，数据库 dump 不变。此重放是接口验收辅助步骤，不假称成功页面还能重复点击已禁用的提交按钮。

## 支持的示例输入与边界

| 精确文本 | 正确入口/上下文 | 本轮使用 |
|---|---|---|
| `C 款黑色 L 全部改藏青` | 提交改单，选择 SO-1001；会先澄清风险。 | 主线实跑 |
| `只改未开裁` | 同一任务回答风险问题，再运行 worker。 | 主线实跑 |
| `SO-1001 把未发的 40 件黑色 M 改成白色 M` | 独立新库中的 SO-1001 改单；README 的现货备用示例。 | 已登记 fixture，本轮不混入主线 |
| `新建订单 华东服饰 A 款白 M 30` | 独立“新建库存订单”入口，不选择已有订单。 | 已登记 fixture，本轮不混入主线 |

这些不是自由语言模板，不可任意替换客户、SKU、数量、空格或标点。本轮在另一新库实测 `C 款黑色 L 全部改藏青。`（多一个句号）得到 `FAILED / FIXTURE_NOT_FOUND`，没有订单或库存业务写入，也不调用 live。失败输入仍可能推进订单意图、使旧批准失效，所以不要在主线等待批准时插入失败样例。其他辅助/失败 fixtures 见[登记代码](../app/orchestration/fixtures.py)；不能把它们算作通用文本理解能力。
