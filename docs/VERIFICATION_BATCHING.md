# 核验批量读取与写锁成本

基线为 PR #61 `dfbac7e6cff2c2a8826935f4384e16b3a054b4e9`，main 仍为 `f5e8ecd`，
PR #60 仍为独立草稿 `1de016e`。本轮只优化事实读取，不修改租约、`data_version`、
锁内复核、结果标记事务或重试预算。旧组合评估不作为本轮 CI。

## 查询与索引分析

原实现按每张订单读取当前行，并在下游核验中调用 `_load_lines`；后者还读取发货、裁剪、
链接及生产采购单，但下游核验只使用 `ordered_qty` 和 `fulfillment_mode`。
额外 1000 张 STOCK 或 500 张 MTO 订单都会使结果写事务执行 6038 条 SQL，包含重复装载。

在实际 SQLite schema 上执行 `EXPLAIN QUERY PLAN`：

| 查询 | 原访问方式 | 本轮处理 |
|---|---|---|
| 当前订单修订 | 唯一索引 `(order_id, revision_no)` | 一次联接选择当前修订 |
| 修订的订单行 | 主键索引 `(revision_id, sku_id)` | 批量联接读取当前行，不装载历史行对象 |
| 每单下游链接 | `SCAN downstream_link`，无 order_id 索引 | 一次读取后按订单及单据分组取最大 link_seq |
| 单据快照 | 唯一索引 `(doc_type, doc_id, rev_no)` | 联接当前生产单版本，只装载有关联的当前快照 |

索引单独试验只在临时合成库增加 `downstream_link(order_id)`：500 张 MTO 的持锁中位
由 1184.041 ms 降到 864.635 ms，但 SQL 数仍为 6038。该索引不能消除逐单往返/ORM 装载。
因此本轮选择批量读取，不增加迁移或生产索引。

## 保持的一致性范围

- 继续检查全库订单、库存流水/余额、预占与发货事实，没有缩小到当前 operation 的订单。
- 当前行通过 `SalesOrder.current_revision = OrderRevision.revision_no` 联接；缺修订仍报错，
  当前行与发货事实仍取 SKU 并集，历史行不替代丢失的当前行。
- 链接按 **订单 + doc_type + doc_id** 选最新序号，保留 `_current_links(order_id)` 的原规则。
  另一个订单上的更新链接不能隐藏本单的旧关联。
- 生产/采购单使用关联 ID 的 SQL 子查询批量装载，无长参数列表；未关联单据仍在原核验范围外。
  生产快照仅装载对应当前 `doc_revision` 的记录，不装载历史 JSON。
- MTO 计划按 SKU 汇总，采购仍按 `(production_order_id, material_id)` 汇总；同一 MO 的多个
  PO 共用需求，不会各自重复计算整份需求。取消、缺失单据及材料规则沿用原逻辑。
- 每次调用都在其当前事务内重新读取，无跨事务缓存。快照失效时仍在原写事务复核，
  写前/复核后的租约检查、旧成功不能覆盖新失败、旧失败不能撤销成功均保持。

## 可复现测量

```sh
env -i PATH="$PATH" HOME=/tmp LANG=C.UTF-8 python scripts/measure_verification.py --samples 3
env -i PATH="$PATH" HOME=/tmp LANG=C.UTF-8 python scripts/measure_verification.py --samples 3 --link-index
```

脚本只创建并删除临时合成数据库；不会接收现有数据库路径。每组预热一次，测量 3 次。
每张新订单有一条数量 1 的当前行及数量 999 的历史行；STOCK 有合法补货/预占流水，
MTO 有一个生产单、分摊需求的两张采购单，每张单据有 3 版快照及链接。
普通读取后由另一个连接修改客户显示名称，强制触发锁内复核。
计时从实际获得结果写锁到事务退出（含提交），不含等待获取锁及单独的领取租约事务。

| 额外订单 | 原持锁中位 / 最大 ms | 批量后中位 / 最大 ms | SQL 原 → 新 |
|---|---:|---:|---:|
| seed | 6.745 / 7.790 | 4.041 / 4.094 | 38 → 19 |
| STOCK 100 | 105.093 / 124.809 | 9.703 / 9.851 | 638 → 19 |
| STOCK 1000 | 909.882 / 945.842 | 106.067 / 111.841 | 6038 → 19 |
| MTO 100 | 214.063 / 268.479 | 16.187 / 17.620 | 1238 → 19 |
| MTO 500 | 1184.041 / 1335.558 | 155.165 / 158.374 | 6038 → 19 |

原 STOCK 1000 / MTO 500 的语句 execute 阶段中位累计约 48.568 / 146.188 ms，
批量后约 0.583 / 1.193 ms；该计时不含结果提取，不能把剩余时间都解释为某一种成本。
在本环境中两个大规模样本持锁中位约缩短 8.6 / 7.6 倍。共享宿主机调度、缓存、数据分布
均会影响结果，不能把这些采样当作生产延迟保证。

## 回归及边界

新增 14 项回归覆盖固定查询上限、历史/当前选择、跨订单链接、未关联单据不装载、
多采购单共享需求、缺单据及全库远端订单损坏；80 张 MTO 下同时覆盖快照失效后复核和
租约到期接管，新失败不被旧成功清除，修复后可恢复。原 head 上 4 项查询上限失败、
10 项语义/并发测试通过；优化后相关套件 204 项通过。
另将当前核验与冻结的 dfbac7e 内核在相同合成数据上对比：30 个健康/故障场景的
一致性问题及下游修复建议完全一致（比较完整结果，忽略无契约保证的列表顺序）。

本地完整 `make check`：**2229 passed、零跳过、3 项警告、覆盖率 95.53%**；lint、格式、
mypy 和全部 19 项 Node 检查通过。离线评测 **53/53**（保障项 23、管线项 30），
普通 wheel 离线安装核对 **116** 个文件、重复初始化通过。
wheel SHA256：`282cbe2d6907d8c12abc3b02f312c93584b77be9e204a1b0512ccad2f19c7ca8`。

本轮没有把锁内工作移出事务或减少事实检查。SQL 次数固定不代表时间、内存固定：
全库行数、链接历史和事实数量仍决定扫描/装载成本，批量映射占用内存也随规模增长。
新查询可能扫描历史行再过滤，但不会将其作为当前事实或装载历史快照对象。
更大规模仍需独立评估查询分区、历史归档或持久事实版本设计，不能以此宣称无界吞吐。

范围复核另发现一个原有盲区：在合成 MTO 订单中删除其唯一当前订单行，保留同修订链接的
活跃 MO/PO（生产数量与采购材料仍彼此一致），dfbac7e 与批量版的两个核验函数都返回空问题列表。
原因是生产数量检查只遍历现存 MTO 行。复现可用 `add_orders(factory, 1, 'mto')`，
删除 `OrderLine('BR-0-2', 'C-BLACK-L')` 后调用两个检查函数。
这属于原有事实覆盖缺口，不是本轮批量读取引入；在本性能基线 47efdb2 中尚未解决。
后续修复已补齐非取消生产事实与当前 MTO 行的键集合检查，采用人工核对提示而非自动取消；
裁剪、取消、到料、历史与丢行恢复回归见 `tests/test_verification_mto_missing_lines.py`。
本节的性能测量和测试数字仍只代表上述性能基线，不代表后续提交的验收结果。

无新增迁移、配置或公共字段；回退至 dfbac7e 恢复原逐单查询成本，保留此前安全保护。
PR 整体原有迁移及排空旧核验进程的升级要求仍适用。未合并、部署或使用真实数据/付费模型。
