# 范围核验第一片：保留批准执行字段

基线为 PR #61 `c96c5a0`。本片实现生产提交证据保存与 `audit-execution` 只读命令，
不是完整的批准 v2、可信父图、共享依赖闭包或自动核验替换。
[后续范围协议](SCOPED_VERIFICATION_DESIGN.md) 和 [共通门槛](LINK_MANIFEST_COMMON_GATES.md) 仍适用。

## 保存什么、凭什么比较

`_commit_locked` 在原有 `BEGIN IMMEDIATE` 内重算执行载荷，确认它同时等于 Plan 和 Approval 的哈希。
在任何业务效果之前复制这份载荷，随后将 `execution_evidence` 记录与业务、批准消费、Operation、审计和 outbox
放在同一事务。Operation 回执保存版本和证据摘要，证据保存原回执身份、批准 ID、请求摘要和规范批准载荷。
唯一键是 operation_id；正常路径只有 INSERT，没有修改、替换、补录或自动修复入口。

这避免了事后从当前订单行或可变 `Plan.normalized_changes` 重建原批准内容。真正保存的是通过哈希重验的
实际载荷；CHANGE 路径在提交时重算下游，所以即使旧 normalized JSON 的下游部分已被修改，也不会保存错误的空清单。
已有批准哈希和请求摘要算法没有改变；不能宣称它们现在绑定了父链或一个以前未批准的完整依赖集合。

读回要求：回执、证据摘要、原 Plan、唯一已消费 Approval、任务和 commit 审计身份相互一致，
保存载荷的哈希匹配原批准；缺失、歧义、未知版本、非法结构或摘要不符都返回 uncertain。
数据库内摘要只证明内部一致性，不是外部签名，不能抵抗拥有数据库写权限者一致改写全部证据。

## 明确覆盖的三个命题

命令：`python -m app.cli audit-execution OP-...`。使用配置中的文件 SQLite 数据库；不迁移、不初始化、不调用模型。
结果以 JSON 输出，固定 `scope=retained_execution_fields`、`global_completeness=not_assessed`、
`authorizes_business_action=false`。

| 字段命题 | 比较的范围 | 不代表什么 |
| --- | --- | --- |
| revision_lines | 指定提交修订的 SKU、数量、履约方式完整集合，以及该修订的 base_revision | 当前订单整体可靠、发货事实或原父图完整 |
| operation_links | 该 operation 应写的 typed doc ID、订单、修订、SKU 的关联集合；检测缺失、额外、重复和错身份 | 单据当前状态、取消锚点完整、所有历史归属正确 |
| reservation_movements | 该 operation 的全部预占流水：序号、仓库、SKU、增量、前后修订及 RESERVE/RELEASE 类型 | 当前共享库存余额正确或全部贡献者来源完整 |

三个字段分别给出 consistent/findings、预期/观察数量及原因码。总体 `consistent_for_retained_fields`
只表示这些字段一致。正常显式空集合计数为 0；缺证据不能变成空集合通过。
跨订单事实关联冲突也会使总体 findings；它不会被请求订单的范围过滤掉。

报告同时列出：目标当前订单图未证明、父图未被原批准绑定、每个下游单据未证明的历史/单据事实、
共享库存闭包未建立，以及当前快照中其他未请求订单的 ID。库存观察包括未发生预占变化的 STOCK 行，
不能因 delta 为空就声称没有共享依赖。观察到的关联/预占 owner 只是事实清册，不证明成员集合完整，
不按 SKU、数量或 PO parent MO 推断所有权。`parent_graph=not_bound_by_approval` 和
`dependency_closure=not_established` 始终保留，包括新创建订单；本片没有创建可信根。

退出码：0=本次保留字段一致，1=发现差异/归属冲突，2=证据不足或无法完成。
退出码 0 不得接到整单/全库健康检查、提交授权或旧 pending 清理上。

## 关键负对照：自动盲区仍存在

保留证据之后，删除当前 MTO 行及订单全部关联，新命令可同时报告行和关联缺失；原 `audit-links`
因无法重建批准载荷而正确报告 uncertain。**旧自动核验仍可能返回空问题并清除 pending。**
回归明确保留这个负对照，它是后续发布阻断项，不是期望长期维持的行为。

若丢失发生在本片首次提交之前，新批准只承诺剩余执行字段；即使这些字段一致，父图仍未证明。
取消后最新 STOCK 操作只保留本次增量关联，不能替代取消操作的历史锚点。本片不把局部通过解释为全图通过。
新报告是独立只读观察，不改变现有 `_post_verify`、重试、租约、pending/manual 或业务批准状态。

## 并发、恢复和限制

提交发生在现有写事务内。批准消费与证据之间没有外部提交窗口，任何保存异常回滚本次业务、任务、
批准、回执和 outbox。成功后进程丢失，新连接能读到完整证据；同键并发只产生一个 operation 和一份证据。
同键重放先返回既有提交身份，不重写证据。原证据丢失时仍承认业务已经提交，并在独立审计中报告 missing；
不能为了恢复证据而重跑业务或根据今天的记录补录。测试中的精确原件恢复是故障实验，不是自动恢复功能。

审计用独立 `mode=ro`、`query_only=ON` 连接及一个显式读事务；不写任何核验结果。
WAL 下并发删除可能发生在读快照之后，所以一次报告仅描述当时读到的状态；下一次读取能发现新损坏。
不提供发布时新鲜度或持续监测保证，不可把旧快照成功交给 `_post_verify`。

每类行/边/流水或清册查询最多读取 1001 条以判断是否超过 1000 条限额；报告及读入证据有 2 MiB 限额，
超限返回 uncertain，不返回截断成功。它不是全规模性能保证，当前依赖观察仍有逐单据/库存查询。
保存端保留完整已批准载荷，不把审计报告的行数/字节限额变成新的业务数量上限，也不截断超限证据。
证据包含原批准已承诺的数据，包括表格来源扩展，需纳入后续数据库备份和保留策略。

## 升级、旧 writer 与回退

迁移 `execution_evidence` 接在 `task_runtime_mode` 后，只新建表和 operation 外键。
不回填旧操作、不改写旧批准或回执、不为旧订单生成可信根，不修改 pending/重试/人工标记。
重复 init 不补造记录。只读命令绕过所有 init；HTTP 仍按既有规则拒绝旧 schema，须显式升级。

生产切换前仍要停止全部 API、worker、watchdog、核验、receipt/cut、导入、seed、CLI、直接 SQLite 和恢复脚本，
排空在途事务并关闭连接/文件描述符，备份数据库/WAL/SHM 一致状态，建立数据库及目录的写权限隔离。
升级后校验实际 schema、外键、业务行/回执保全及 writer 清册，再启动同版本进程。
本轮没有执行任何真实部署切换。

隔离合成库的实际旧代码实验：`c96c5a0` 启动检查拒绝新 schema，但绕过启动检查的旧 kernel/已持有 factory
仍能提交。该操作没有保留证据，新审计返回 `EXECUTION_EVIDENCE_NOT_RETAINED`，没有默认为可信。
这证明迁移不是旧 writer 隔离。外键 OFF 或直接 SQL 仍可删改证据；本片不宣称数据库不可变或任意 writer 安全。
完整可信父链/闭包协议启用前，必须完成独立身份/写服务等实际隔离验收。

空证据表可降级到 `task_runtime_mode`，业务表保持原样；一旦已有证据，downgrade 明确拒绝删除并保留迁移版本。
应停写、保留新库，使用兼容版本恢复；不能删除证据以绕过保护。切换后有新业务时直接恢复旧备份会丢业务事实，
须另行完整对账决策。若本来已损坏丢失证据，重新升级也不会重建它，原回执仍报告 missing。
支持的 engine 上已测试 DDL 前、DDL 后和版本标记时中断均原子回滚；其他外部工具的事务配置不在此保证内。
