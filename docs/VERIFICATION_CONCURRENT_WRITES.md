# 并发无关写入下的核验可用性

本轮基于 PR #61 精确 head `66776c53de3c550674a50c20025542ec23708d28`，
main `f5e8ecd`、PR #60 `1de016e` 均未变化。父任务提供的组合评估是独立组合证据，
没有并入本分支，也不作为本分支的远端 CI 结果。

## 结论与选择

值得在当前 SQLite 原型内做小范围改进。旧实现把任意其他连接的提交视作核验失败，
即使只更新 outbox 投递次数，持续出现也会耗尽预算并转人工。新实现保留 `data_version`
快路径，在版本变化、首次核验成功且仍拥有有效租约时，于结果写事务内复核一次当前事实。
它按事实是否一致判定，无关写入不再直接导致失败；相关事实改变但仍然一致时也可通过新核验。

| 方案 | 判断 |
|---|---|
| 表/字段快照或摘要 | 可减少误判，但需维护另一份完整的核验依赖清单；遗漏新查询依赖会误放行，本轮不引入 |
| 相关表触发器与持久版本计数 | 适合后续降低读锁成本，但涉及迁移、所有写路径及依赖边界，超出本轮小改范围 |
| 所有核验从一开始持写锁 | 会让未发生并发写入的普通读取也阻挡写入，本轮不采用 |
| 仅快照失效时，在结果事务重新核验 | 复用现有一致性逻辑，无新增迁移或依赖清单；选择此方案，并明确写锁成本 |

一次尝试最多执行两遍事实读取，自动预算仍只扣一次。首次读取失败、操作已通过或
已失去所有权时不做锁内复核。复核不会写业务事实、批准订单、重新提交或重置预算。

## 安全依据

1. 保留同一物理连接的 `data_version` 比较；读事务结束后获取 `BEGIN IMMEDIATE`，
   在实际获得锁后重读 operation、检查 token 和期限。旧所有者不能进入复核或写结果。
2. 快照未失效时保留原有快路径；失效时不使用旧成功，而是在同一结果事务内运行相同的
   `consistency_problems` 和 `downstream_problems`。SQLite 写锁阻止其他连接在复核与标记之间提交。
3. 复核后再次读取时钟检查所有权/期限。租约到期、事实不一致或异常均不清 pending；
   进程退出回滚结果事务，待租约到期后仍可按原预算恢复。
4. 已通过状态继续保持；旧成功覆盖新失败、旧失败覆盖新成功的既有回归保持通过。

锁的语义依据 [SQLite 官方隔离说明](https://sqlite.org/isolation.html)，
版本比较依据 [SQLite data_version 说明](https://sqlite.org/pragma.html#pragma_data_version)。
代码没有创建一份独立的表/字段允许清单，核验逻辑新增依赖时，复核调用同一逻辑。

## 复现与回归

`tests/test_verification_concurrent_writes.py` 的最终 16 项用例在只加入测试的
`66776c53` 源码归档上均失败，修复后的相关套件 190 项通过。覆盖：

- 首次、自动及人工核验每次普通读取后都出现无关 outbox 更新，自动核验不再耗尽预算。
- 库存余额、订单行、生产单、采购单、单耗、单据快照、下游链接发生实际不一致时仍失败，
  恢复故障后正常通过；合法的新订单修订用新事实核验。
- 两个并发核验者更新各自 operation，不会仅因彼此的核验元数据提交而相互阻断。
- 锁内异常、模拟进程退出、租约恰好到期均保留 pending 和恢复资格，业务表保持不变。
- 独立线程验证锁内其他连接仍能读取，但写入被锁阻挡；核验结束后写锁释放。
- 既有 14 项结果 fencing/发货事实用例，以及重放、watchdog、worker-loop、日志、人工恢复继续通过。

## 合成持锁成本与限制

在本云环境的文件型 SQLite WAL 上，每组预热一次，再记录 5 次核验。扩展订单每单只有
一个 STOCK 零数量当前行，没有新增下游链；在普通读回结束时由另一个连接更新客户显示名称。
计时从实际取得结果写锁到事务退出，包含提交；不计领取租约的独立事务或等待取得写锁的时间。
这是诊断采样，不是压力测试、生产吞吐或延迟保证。

| 额外订单数 | 无中间提交，持锁中位 ms | 无关提交后复核，持锁中位 / 最大 ms |
|---|---:|---:|
| 0 | 1.077 | 6.349 / 8.105 |
| 100 | 1.335 | 75.383 / 87.079 |
| 1000 | 1.583 | 688.717 / 817.596 |

成本随全库事实扫描增长。锁内复核会延迟其他写入；更大数据、复杂下游、较短租约或锁等待
仍可能导致失败/转人工。本轮消除“仅因无关提交就判失败”的路径，不保证所有负载下无饥饿。
扩大规模前应测量真实的合成业务分布，并评估版本计数或按订单限定核验范围的独立设计。

## 兼容性与回滚

无新增数据库列、迁移、配置或公共字段；PR 整体原有 `sync_dispatch_receipts` 迁移仍保留。
升级前排空旧核验进程；回退到 `66776c53` 会恢复无关写入导致 pending/预算耗尽的行为，
更早版本还会暴露旧结果覆盖缺口。此前已通过的操作不会自动重新核验。

没有合并、部署、真实客户数据/ERP、付费模型或真实浏览器测试；自由语言能力未评估。
