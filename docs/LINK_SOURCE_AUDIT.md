# 独立只读关联来源审计

基线：PR #61 `bf94279e7d04ecbe23d741a22aaddf24138c1c17`。
`python -m app.cli audit-links OPERATION_ID` 读取 `OOS_DATABASE_URL` 指定的已存在 SQLite 文件，
审计一个保留的提交操作应写入的历史关联。输出 JSON；不需要启动应用或 worker。

它不修改业务、Operation、pending、重试计数、租约、审批、任务或 outbox；不初始化数据库、
迁移、重试提交、修复关联或调用模型。它不接入现有提交后的核验路径，不是业务放行门禁。

## 何时能证明预期关联

只有以下证据全部成立，才使用计划的 `normalized_changes.downstream` 作为该次提交的完整清单：

1. Operation 与 Plan 都为 COMMITTED；提交回执的计划、任务、订单、chain 和修订身份一致。
   Task 仍指向该操作；订单修订存在，修订号为计划 base + 1，订单当前版本不落后于它。
2. 恰好一个 CONSUMED Approval 指向该操作；计划哈希、意图版本、审批人、提交审计记录和
   Operation 请求摘要一致。过期时间及任务的当前执行状态不被误用来否定历史已消费批准。
3. 清单为显式数组，单据类型、ID、订单行标识及结论形状受支持，单据键不重复。
   `downstream` 缺失不能当成空数组；当前实现只支持 create/change 提交协议。
4. 使用该次提交的 OrderRevision/OrderLine、该 Operation 的 StockMovement、计划保存的
   expected stock/doc revisions 和 downstream，重建现行 v1.0 批准载荷并验证哈希。
   库存流水须与预期库存版本、W1、序号、增量和 RESERVE/RELEASE 类型一致；表格来源扩展
   `sheet_order_v1` 也参与哈希。重建不使用今天的库存、发货、裁剪、单据状态或数量。

经验证的每条清单项在提交事务中都应产生一个 DownstreamLink，精确对应：
`operation_id + doc_type + doc_id + order_id + order_revision + order_line_sku`。
检查该操作的关联集合：缺失、错身份、重复和额外关联分别报告。link_seq 的原值没有独立记录，
本审计不猜测缺失序号或将序号连续性当作完整性证明。

本证明依赖保留证据的内部一致性，哈希不是外部签名。它不重放原始自然语言，不认证客户意图，
也不能抵抗计划、批准、审计和所有哈希一起被一致重写。未纳入批准载荷的来源文字等字段不在此审计范围。

## 输出与不确定性

| status / 退出码 | 含义 |
|---|---|
| `consistent_for_operation` / 0 | 该操作的可验证历史清单与现存历史关联一致；包括合法新建 STOCK 订单的空清单 |
| `findings` / 1 | 清单已经验证，存在 `EXPECTED_LINK_MISSING`、`LINK_IDENTITY_MISMATCH`、`DUPLICATE_LINK` 或 `UNEXPECTED_LINK` |
| `uncertain` / 2 | 证据缺失、损坏、不支持、身份矛盾、哈希不能重建、超限或数据库不可读；不得解释为通过 |

报告固定注明 `global_completeness=not_assessed`、`current_ownership=not_assessed`、
`authorizes_business_action=false`。不确定时不输出部分清单或“已证明缺失”的猜测。
输出仅含关联身份、计数及稳定原因码，不导出计划正文、原文、来源摘录、幂等键或租约 token。

| 场景 | 处理 |
|---|---|
| 当前及全部历史关联被删除，提交证据仍完整 | 精确报告该操作缺失的边，不靠 SKU/数量推断 |
| 零数量生产/采购单关联被删除 | 若该次哈希清单列出它，仍能报告缺失 |
| 取消后再修改 STOCK | 取消操作保留当时的清单；后续操作不要求重新链接已取消单据 |
| 后续修订改变颜色、数量或单据状态 | 按各自历史清单检查，不用最新内容替代历史证据；新版链接不能替代丢失的旧版链接 |
| 计划或历史订单修订缺失、哈希清单被删改 | `uncertain`，不根据现存数量补清单 |
| 当前 MTO 行和全部关联同时丢失 | 批准哈希不能重建时为 `PLAN_HASH_UNVERIFIABLE`，不能声称具体关联已被证明；恢复可信行后可进一步报告断链 |
| seed、导入、未关联单据或已丢失全部提交来源 | 无可验证 Operation 时不能建立归属；不按 SKU、数量、父 MO 或命名规律补链 |

旧文中的“保留计划能证明关联”有上述完整性前提。仅剩一份未经哈希核实的 JSON 清单不是充分证明。
同样，历史关联一致不表示当前单据存在、内容正确、当前订单完整或可继续提交业务。

## 只读与并发边界

命令在普通 CLI 初始化前分流。专用连接使用 SQLite URI `mode=ro` 和 `query_only=ON`，
显式 `BEGIN` 后所有读取共用一个快照，退出回滚并销毁连接。文件不存在时不创建目录或数据库；
不接受内存库、非 SQLite 数据库或带查询参数的 URL。文件名中的空格、Unicode、`#`、`%` 按字面处理；
`?` 在数据库 URL 中属于查询分隔符，此入口不支持该文件名写法。

WAL 下其他事务可并发提交；本次报告描述首次读取时的快照，不能保证输出时仍最新。
没有业务动作消费本报告，旧报告不能清除 pending 或覆盖新的核验失败。
读连接可能使用 SQLite WAL/SHM 辅助文件；不承诺文件系统零活动，但所有数据库记录保持不变。

每项集合最多 1000 行，JSON 报告最多 2 MiB，超限返回不确定而不截断成功报告。
此限制不是全库扫描、存储中 JSON 大小或延迟上限；某些 operation_id 查询仍可能扫描历史表，
长读事务可能延迟 WAL checkpoint。本轮不在业务写锁内运行审计，也不新增索引或迁移。
回退代码仅移除此审计入口，不需要数据回滚；PR 既有迁移要求保持不变。

## 后续预期关联清单设计（尚未实施）

后续架构分析和可执行合成实验见 [预期关联清单设计](LINK_MANIFEST_DESIGN.md)。
新一次有效批准不能证明旧来源完整；将清单接入自动核验前，必须先处理可信基线与核验范围。

若需要更低成本、覆盖 seed/导入并减少对历史订单行的依赖，建议在原业务提交事务中写入版本化
manifest header 与 edges：header 绑定 operation、订单/修订、格式版本、边数和规范化摘要；
edge 保存明确的单据类型/ID、订单行标识及取消/重链语义。建立 operation+单据键唯一约束，
以及 operation、订单修订、单据身份索引；提交回执同时绑定 header 的版本、边数和摘要。

seed/导入须显式登记 managed/unmanaged 来源和可追溯证据，不能无证据回填归属。
取消后的历史边仍保留，新的清单只记录新提交实际承诺的边。版本升级、保留期限、历史缺口和
证据损坏须有明确的不确定状态。即使增加清单，清单与所有回执一起丢失仍需要外部可信备份。
