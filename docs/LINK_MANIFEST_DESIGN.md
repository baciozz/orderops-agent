# 预期关联清单：设计与合成事务验证

状态：**尚未实现生产协议、迁移或自动放行门禁**。基于 PR #61
`c565051386944b09827003d11fe5003a2dc64fee`，2026-11-06。
本次只增加本设计及测试目录中的实验。`main` 仍为 `f5e8ecd`；PR #60 独立存在，不能视为 main。

结论：SQLite 可以将业务写入、批准消费、清单及回执绑定放在现有同一事务中，
但“增加一张清单表”不足以安全覆盖旧库。现存资料不能证明所有历史归属完整；
新批准也不能修复这种认识上的缺口。需要先决定旧来源接纳规则和核验范围，
再实现完整协议。当前自动核验的“行与全部关联同时消失”盲区仍在。

| 独立关系模型的延迟复合外键 | 当前版本与 manifest 指针绑定可在事务提交时拒绝无 header 的修订；正常原子写入可通过。此模型尚非真实 Alembic 迁移 |

测试中的 `existing_*` 是当前缺口的证据，**不是应长期保持的产品行为**；完整协议上线时应替换为拒绝/不确定的断言。
`tests/manifest_transaction_probe.py` 仅在 pytest monkeypatch 下给真实 kernel 事务追加实验表，
固定标记 `scope=operation_only, origin_completeness=unknown`，没有自动清除 pending 的入口。
它不是可复用的生产解析器：完整输入校验、大小限制、全部证据身份、根与父链和图转移仍须实现。
进程丢失使用提交后异常及重新打开连接模拟，未模拟操作系统断电或磁盘损坏。

## 现有写入与核验架构

`commit_plan` 的 `BEGIN IMMEDIATE` 包住 `_commit_locked`：先处理幂等键，再校验批准、意图、
订单与库存/单据依赖，重新计算 `_payload` 并比对 Plan/Approval 哈希，然后写修订/行、预占/流水、
下游单据及关联、事件/outbox、批准消费、提交回执和审计。退出事务后才 `_post_verify`。
安全插入点是**哈希校验后的实际执行载荷及同事务的回执写入**，不是提交返回后的异步补写。

现有 `downstream` 是该次提交应追加的关联集合；取消单据在后续操作的加载范围外。
SalesOrder 没有独立来源完整性标志，ProductionOrder 没有归属订单外键，
DownstreamLink 的 operation_id 可空。SKU、数量、父 MO、ID 命名都不能证明订单归属。

`_verification_problems` 检查全库库存和下游事实。`_post_verify` 使用固定连接读取 data_version，
写结果时在 `BEGIN IMMEDIATE` 内校验所有权和租约；任何其他连接提交后重做事实检查，
最后再次检查租约。新清单校验必须进入同一检查函数和事务，不得另设可清 pending 的捷径。
已有核验不承担阻止所有后续业务提交的职责；生产清单协议还必须在计划及提交前校验可信基线。

## 推荐协议：每次执行回执与当前完整归属图分开保存

以下均为待实现设计。

1. **执行清单**保存这次批准实际承诺写入的行、库存增量、下游效果和精确关联身份。
   从冻结的实际批准载荷取值，与 `_apply_downstream` 共用同一份经过校验的数据。
2. **当前归属图**保存完整的当前订单行集合及所有已被可信证据归属的单据身份；
   保留取消和历史锚点。由可信父图加本次批准的精确转移生成，不能从现存边重新推断。
3. **来源根与可信度**独立记录。只要父图或根未知，后次新批准不能把它提升成完整。
   `VERIFIED_FROM_CREATION`、`ATTESTED_IMPORT`、`LEGACY_UNKNOWN` 必须区分；人工接纳是有范围的
   明确声明，不是算法证明丢失证据真实存在。用户需决定是否接受这种来源及其适用范围。

建议关系模型：

| 实体 | 必须保留/约束的内容 |
|---|---|
| ManifestHeader | 格式与协议版本，订单/修订，operation/plan/approval，父清单 ID+digest，来源根及状态；规范载荷、行/边计数与摘要；每订单修订唯一、每操作唯一 |
| ManifestLine | 完整批准行集：SKU、数量、履约方式；唯一 manifest+SKU；空集合必须有显式 header 与 count=0 |
| ManifestEdge | typed doc ID、订单行身份、生命周期、关联修订、来源 operation/manifest、精确关联序号/ID；唯一 manifest+doc_type+doc_id；数量零不意味着可丢弃 |
| ExecutionEdge | 本次实际承诺的新关联身份；与完整图的继承历史锚点分开，不强迫取消单据重链 |
| Order manifest pointer | 当前订单/修订/清单的复合约束，不能只有一个允许任意空值的旁表 |
| Operation receipt | 清单 ID、格式/协议版本、digest、明确计数；与已消费批准和请求摘要一致 |
| ProvenanceRoot | 明确的创建/导入/人工接纳事件、可用证据及范围，不使用 seed 名称或 SKU 模式作为证据 |

为 operation、order+revision、manifest+typed-doc-key 建唯一键及索引；不得全库反复重建历史 JSON。
校验应批量读取当前清单和必要锚点，避免锁内 N+1。完整历史不能无上限追溯：
保留完整当前图及受控的已校验检查点；检查点来源、链截断及保留期限需单独协议。
在上述协议完成前不承诺能减少锁时间，也不引入清单缓存放行。

### 批准绑定与事务顺序

新增批准协议版本，规范载荷纳入 base manifest 的 ID、digest、版本、来源根/状态，
以及本次提议的完整行集、关联图转移和执行效果。采用明确类型与确定排序；
拒绝重复键、不支持类型、bool 冒充整数、负版本、缺少清单、大小超限及未知协议。
绝不能通过 `value or []` 把缺失值变成合法空集合。

新 operation/order ID 在提交时才分配。批准载荷应使用明确的 `this_operation` / `new_order`
逻辑占位并绑定 task/plan，保存规范批准表示；提交后以已分配身份确定性实例化，
再生成回执摘要。不得把尚未存在的随机 ID 写入批准后临时重算 Approval.plan_hash。

计划与批准阶段读取并验证可信父图；提交的 `BEGIN IMMEDIATE` 中重新校验父指针/digest、
当前行/边集合、原业务依赖、意图、完整批准哈希，才执行。即使 SalesOrder.current_revision
不变，父清单证据变化也必须使旧批准失效。迁移前批准不含这些绑定，必须重新规划/批准，
或走明确的旧协议不确定路径；迁移不能伪造“已由用户批准”的新字段。

分配新身份后，在同一事务写业务修订、完整清单及执行边、批准消费、回执绑定和 outbox。
约束或任何写入失败整体回滚；不能先 COMMIT 再补清单。新订单暂存 rev=0 的当前创建顺序
也需纳入延迟约束方案，不能为兼容旧写法留下永久 NULL 指针。

幂等键命中时校验原请求和原回执绑定，返回同一 operation；不再写业务，也不重建/覆盖清单。
若原证据已缺失，保留“业务可能/已经提交”的事实，返回稳定的核验不确定状态，进入人工恢复，
而不是返回可导致调用方换键重提的普通未提交错误。实验的 RuntimeError 仅用于证明零修复写入，
不是所建议的生产 API。提交后崩溃只重做核验/确认，不重做业务。

### 取消、历史、部分尾单及新采购

- 普通保留/改色/部分尾单：明确记录批准前后身份和实际效果；不按数量分摊归属，
  不覆盖已裁剪/已收货事实。混合 STOCK/MTO 的完整行集合都参与校验。
- 取消：从可信父图继承取消边，指向当时的取消修订/操作和对应 DocRevision；
  当前图可引用真实存在的过去修订，但不能接受未来、缺失或属于别的订单的修订。
  取消关联不因零数量或后次 STOCK 修改而消失，也不重链到后次修订。
- 历史：后次有效关联不能替代前次丢失的执行边；历史审计与当前归属检查要分别说明范围。
  若允许删除历史明细，须有独立的保留与可信检查点协议，不能自动忽略。
- 采购补单：仅采纳批准中明确的新 ID、parent MO、订单行、supplier 及 exists=false 依赖，
  提交再次验证 ID 未占用；不能看到同 SKU 或某 MO 的采购单就自动收编。
- 未管理单据：单据可合法存在而没有订单关联。没有可信根/执行证据时只报告 unknown，
  不能用 PO 的 parent MO 反推其所有权，更不能自动补链或修业务记录。

### 自动核验与恢复

先校验协议/可信来源、header/receipt/批准/父图绑定及计数/摘要，然后比较当前完整行集、
执行边和归属图对应的真实边集合，再使用现有单据快照、执行事实和库存不变量。
必须识别额外、重复、错订单/修订/类型的边；不能只检查预期边是否存在。
missing、unknown、unsupported、corrupt 各有稳定原因码，都不能解释为通过。
摘要提供内部一致性，不是外部签名；所有表和摘要被一致改写、或订单和全部来源同时被删除，
仍需要外部可信根/备份才能发现。

所有这些读参与当前 `_post_verify` 的同一快照/写结果事务；data_version 变化时必须重查清单
及业务事实，不只重查旧业务函数。旧 token、租约到期、接管、新失败都不得被旧成功覆盖。
损坏需要精确可信备份或明确的人工接纳流程；重试只重复检查，不能自动“修好”header/边。
未知范围应在独立 coverage 状态中保留，历史已 false 的 pending 不能被迁移静默解释为清单已验证。

## 迁移、旧库及回退边界

当前 Alembic head 为 `sync_dispatch_receipts`；启动不会迁移，`schema_ready` 核对已知最新版本及
表/列名称，不验证业务值或约束。新增协议将需要正式 migration，不能靠 `create_all` 或启动补数据。

推荐的迁移步骤（未执行）：

1. 停止所有旧 API、worker、watchdog 和导入写入，备份可恢复的一致数据库；明确协议切换点。
2. 结构迁移只建立表、索引、约束和明确的旧来源 `LEGACY_UNKNOWN` 占位；记录当前订单清册，
   不生成证明关联完整的边，不消除 pending/manual/retry 历史，也不改写旧批准哈希。
3. 非空 pointer 与延迟复合 FK 的实际 Alembic batch 重建必须验证：已有 FK、CREATE rev0、
   取消、迁移中断恢复、repeat init、索引、旧 writer、foreign_key_check、升级/回退数据保全。
   占位 header 是 unknown，不得被唯一键或外键“证明”为可信。仅增加表或版本标记并不足够。
4. 旧库清单的候选材料可来自只读来源审计，但它只证明单次操作，不能证明基线完整。
   对无法建立来源根的订单保持 unknown。保留原始证据，不尝试按数量/命名自动回填。
5. 重新规划/批准跨协议的待执行计划；核验覆盖状态与旧 pending 的展示/调度规则确定后才启用。

回退不能只删清单表继续声称已核验。安全方案是停写后恢复切换前一致备份，
或保留新库只读并使用明确支持降级证据状态的兼容版本。若切换后已有业务提交，
直接恢复旧备份会丢这些事实，需要完整导出/对账与人工决策，不能自动执行。
旧二进制拒绝未知迁移是必要的启动保护，但实验已证明它不能阻止仍运行的进程写入。

本次只添加文档/测试，无 schema、业务或部署变更；回退本次提交无需数据迁移。

## 必须先决定的产品语义

| 选择 | 结果/代价 |
|---|---|
| 保持现有“全库通过”含义，任何旧来源 unknown 都不放行 | 最保守且语义一致；有未知旧订单时会阻塞全库自动核验，需要可信基线接纳或重建 |
| 定义按可信来源管理范围的部分核验 | 可分阶段接入新订单；必须新增明确覆盖范围与 unknown 展示，不能把部分通过映射成原来的全库通过；库存共享等跨订单依赖也必须计算，不能简单过滤订单 |
| 若整个环境可丢弃，重新建立有创建根的纯合成数据集 | 可验证从创建到取消的全流程；必须明确授权重置，不能假设现有库是可丢弃数据 |

建议先确定是否接受有记录的人工基线接纳、旧库是否可重建，以及是否继续保留全库核验语义。
未决之前，不接入自动放行、不暗中设置可信、也不修改旧数据。

## 验证完成度与下一步验收

本轮覆盖真实 kernel 事务的原子性/重放/并发，批准载荷取值，生命周期与补单身份，
当前来源盲区、过期读和关系约束原型。原有租约/接管/结果新鲜度回归应继续运行。
这些结果不能当成以下内容已经完成：

- 正式 schema/migration/downgrade、数据库层防止旧 writer 和多协议升级的端到端验证；
- 批准 v2、可信父图转移、导入接纳、历史检查点、覆盖范围产品实现；
- 全库自动核验的清单检查、未知状态 UI/API、全规模锁持有时间和故障恢复验收；
- 真实浏览器、真实 ERP、自由语言能力或外部模型效果。本轮不调用这些服务。

完成产品选择后的实施门禁应包括：旧/损坏/空库迁移、NULL/bool/未知格式故障、同键/异键并发、
批准后父清单变化、原子提交各阶段故障、崩溃恢复、旧成功覆盖新失败及租约过期、
取消历史/部分尾单/补单和混合库存、所有来源缺失时始终不放行、规模与锁测量、完整 make check、
离线评测和 wheel migration smoke。PR #60 只做隔离组合验证，不将它称为远端 CI。
