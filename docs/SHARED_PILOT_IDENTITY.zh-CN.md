# 共享试点：身份、订单授权与审批验收草案

**当前结论：尚不能开放共享试点。** 本轮在 `fa453049c0c814837a704606e0a6ab52820a5779` 的运行代码上完成28个真实本机 HTTP 请求，使用全新合成库、FIXTURE 和独立客户端 A/B/匿名客户端。A/B 只是测试标签，不是已认证用户；没有创建账号、凭据、登录会话或 OAuth grant。没有改动应用认证、业务规则或数据库结构。

| 合成流程 | 实际结果 | 能证明什么 |
| --- | --- | --- |

## 最小方案的共通门槛（待实现）

以下是候选方案都必须满足的安全契约，不是本轮已经交付的权限功能。先按“主体、动作、资源范围”描述权限，具体授予谁、如何组织成角色仍需决定。

| 操作 | 所需身份、范围及审计 |
| --- | --- |
| 首页/列表、订单/任务、来源、差量、导出、审计、回执 | 先认证再按范围过滤；按 ID 直取和下载也检查同一规则。任务、来源、计划、批准、operation 通过服务器关系定位订单，不能信任请求自报的 order_id/tenant_id。列表总数及错误响应不能泄露隐藏对象。 |
| 创建需求/订单、上传、回答、改绑、取消、规划 | 检查提交/修改能力及目标订单范围；未解析的新任务先绑定创建主体。解析出订单后必须重新检查；不能用模型建议、SKU 相同或未知来源推断授权。输入也会使旧审批失效，不能视为无害操作。 |
| 批准/重新批准 | 从服务器验证后的稳定主体标识记录批准人；不使用 body、昵称或任意转发头。绑定订单、计划摘要、意图/依赖版本和批准有效期，并记录当时授权上下文；界面显示真实批准人。 |
| 提交/同键重放 | 先验证当前主体和资源访问权限，再查回执；在业务事务的最终授权点重验权限，不能仅凭拿到 approval_id 放行。继续保留现有版本、库存、幂等和租约检查。批准人、实际执行主体和委托关系分别可追溯。 |
| 库存、生产/采购及共享依赖 | 订单权限不能自动扩展为所有库存/下游单据权限。需明确仓库和相关单据范围；未知归属不自动授权。已有 partial 核验不构成完整来源证明或授权。 |
| worker、核验重试、配置、迁移/备份、直接 SQL/文件 | 服务身份与人的权限分开，工作者不得代替人批准；队列保留发起主体和授权范围。拒绝绕过 HTTP 的旧 writer/CLI；服务库及原件只由受控进程访问。只加登录页不能形成边界。 |

由此得到的最小接入切片是：可信身份入口 → 服务器会话/主体 → 统一动作与对象授权 → 事务内重验 → 可追责审批及回执。默认拒绝未知主体/范围，授权拒绝不创建计划、批准、operation 或模型预算；可单独记录安全审计。演示路径不能在共享配置下继续使用 `demo-user` 放行。

现有内核要求提交身份与批准人一致。采用“审批人与执行人不同”的流程需要显式设计委托及审计，不能只替换 HTTP 的 actor 字段。身份、会话和权限撤销的传播上限与最终授权点也必须明确：撤销在授权点前生效则拒绝；已提交的业务不能被后续退出登录假称回滚。

## 过期与恢复的验收契约

1. 未登录/无效或过期会话：受保护 API 返回明确401，页面保留用户尚未提交的编辑并引导登录；不自动重发写请求。已登录但无资源权限，使用统一403或不泄露存在性的404策略。真实 Cookie、CSRF、回调与代理边界需在选定方案后测试。
2. 批准之前会话过期：重新登录后回到原任务、重新检查当前范围和计划状态。登录不会延长批准 TTL、恢复已撤销批准或自动执行。
3. 批准之后、提交之前会话过期/权限撤销：拒绝本次提交且无业务副作用；恢复身份后核对原批准是否仍有效，过期则显式重新批准。是否要求近期重新认证以及期限值待产品/组织策略决定。
4. 已提交但响应丢失：重新登录后，只有仍有权限的主体才能使用原键查回同一 operation；不能因登录切换新建提交键。另一主体不能凭旧 URL、键或 Cookie 得到回执或接管批准。幂等键须绑定主体/组织、操作与请求内容。
5. 权限撤销与提交并发：用确定性交错测试最终授权点；拒绝路径不写业务，成功路径至多一次并保留真实主体及授权版本。跨服务撤销不能未经证明就宣称即时生效。

当前只能验证批准过期和原键幂等；真实会话过期、退出、撤权、登录后恢复均**未实测、未实现**。

## 待选择的产品边界

| 决策 | 选项与影响 |
| --- | --- |
| 身份从哪里来 | **已有组织 IdP，经受控网关接入**：可复用账号/MFA，但必须封闭直连应用并验证网关身份，不能直接信任客户端头。**应用直接接 OIDC**：主体/会话由应用处理，增加回调、令牌验证与会话维护责任。**自建本地账号**：适合无 IdP 的封闭试点，但增加密码、重置、MFA、撤销与运维责任。尚未选定或连接任何服务。 |
| 谁可提交、批准及执行 | **同一获授权者可自审自提**：步骤少，但缺少双人复核。**提交人与批准人分离**：更能防止误操作，需安排第二人及缺席处理。还需选择由批准人执行，还是允许另一个具备执行能力的人按明确委托提交；管理员不应自动拥有业务批准权限。 |
| 单一组织还是多租户 | **单一组织、订单/仓库范围授权**：试点范围较小，仍需控制任务、文件和共享库存读取。**多组织/租户**：租户键必须贯穿数据、原件、队列、回执、缓存及审计；共享仓库/供应商的归属与数量可见性需另行决定，不能只加 tenant_id 请求字段。 |

决定前可继续完善合成验收与设计，但不迁移现有业务身份，不把历史 `demo-user` 归给某个真人。历史批准/任务的归属与可见范围需明确的导入规则；未知归属默认隔离，不能静默授权。切换需停旧 writer 并保留一致备份；身份层上线后不能回滚到共享运行的无认证版本。具体迁移与回滚尚未执行。

选定身份方式后，用隔离身份夹具提供稳定主体 A/B/C、短期测试会话、明确的订单能力集合；这些夹具不连接真实组织、不创建真实 OAuth grant。以下均为**待执行门禁**：

| 用例 | 预期结果 |
| --- | --- |
| 无会话、伪造 body/header/Cookie；绕过网关直连 | 未授权读写均拒绝；只有可信验证链能生成主体；批准人不可冒充。 |
| A 有 SO-1001 权限，B 仅有 SO-1002 权限；C 只读 | B 替换订单/任务/来源/计划/批准/operation ID、下载链接及幂等键均不能越权；C不能上传/回答/取消/批准/执行。角色名称不重要，能力集合由已选政策给定。 |
| 合法 A/B 按所选审批分工走文本或表格流程 | 风险澄清→批准→提交成功；审计中的创建、批准、执行主体与实际认证主体相符。 |
| 过期、退出、撤权发生于批准前、批准后、最终授权点前 | 未提交动作拒绝；原任务可在重新认证后按当前权限继续，业务/预算无越权副作用。 |
| 提交成功但响应丢失，再登录后原键恢复；切换成另一用户 | 授权主体取回原 operation，重复次数不增加；其他用户不能读取或接管。 |
| 旧任务、未知归属、共享库存与下游资源、服务身份 | 未知范围不放行；工作者不能伪造人工批准；历史数据不自动认证，所选隔离范围无泄漏。 |
| 真实浏览器会话流程 | 验证 Cookie、跨站请求、退出、多标签页/刷新和编辑恢复；HTTP 头实验不能替代这一项。 |
